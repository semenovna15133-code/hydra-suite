## 1. МИССИЯ И ПРОДУКТ
═══════════════════════════════════════════════════════════════════

Hydra Suite — продукт для продажи VPN-доступа конечным клиентам в условиях
блокировок (основной рынок — РФ) с полным циклом: выдача ключа → подключение
без настроек → обход DPI → продление → восстановление при потере.

Главная фишка продукта: АВТОМАТИЧЕСКИЙ выбор протокола и сервера.
Клиент не выбирает технологию — приложение само определяет, что работает
в текущей сетевой обстановке, и переключается незаметно для пользователя.

Три компонента экосистемы:

  ПАНЕЛЬ (hydra-panel)   — инструмент АДМИНИСТРАТОРА. Управление серверами,
                           протоколами, клиентами, ключами, метриками, DR.
                           Клиент никогда не обращается к панели.
  БОТ (hydra-bot)        — витрина ПРОДАЖИ и поддержки. Выдача ключей,
                           продление, восстановление, напоминания.
  КЛИЕНТ (hydra-client)  — приложение КОНЕЧНОГО ПОЛЬЗОВАТЕЛЯ. VPN с кнопкой
                           AUTO, split tunneling, статистика.

## 2. РОЛИ И ГРАНИЦЫ КОМПОНЕНТОВ
═══════════════════════════════════════════════════════════════════

Панель:
  - деплой протоколов на VPS по SSH (onboarding одноразовым паролем)
  - выпуск/продление/revoked ключей, привязка к клиентам (telegram_id)
  - метрики, алерты, отчёты, SQL-консоль, бэкапы + DR
  - НЕ доступна клиентам; защищена Hydra Auth v1

Бот:
  - продажа: /start → привязка telegram_id → выдача Key File v2
  - поддержка: /restore (по telegram_id), /extend, /status, /devices
  - напоминания о продлении: 7д / 3д / 1д / истёк
  - канал экстренных обновлений split-профилей и новых endpoint'ов
  - magic-link /login для входа админа в панель

Клиент:
  - говорит ТОЛЬКО с VPN-серверами (и с публичным зеркалом split-профилей)
  - не знает о панели; не хранит её адрес
  - работает автономно: ключ самодостаточен, Smart Connect локален
  - НЕ использует HTTP API панели (/api/v1/client/* — legacy, Р-22)

Правила протоколов:
  П-01  Default-протокол при чистой сети: AmneziaWG 3.1 (скорость).
  П-02  При признаках DPI (UDP режут, TCP жив): приоритет AIVPN/WDTT.
  П-03  WDTT требует доступности VK API; недоступен VK → WDTT исключён
        из пула кандидатов до восстановления доступности.
  П-04  WDTT: 4 VK-хеша — протокольный лимит, не меняем.
  П-05  WDTT: 108 потоков старт, адаптивно вниз: throughput < 10 Мбит/с
        → 64; CPU sustained > 70% → 32. Оптимум хранится per-сервер.
  П-06  VK-хеши создаёт САМ ПОЛЬЗОВАТЕЛЬ в своём VK-профиле и вводит
        в приложение (экран настройки WDTT с инструкцией и валидацией).
  П-07  Размер APK не оптимизируем: все три бэкенда в одном билде.

## 4. МОДЕЛЬ ДАННЫХ БИЗНЕСА
═══════════════════════════════════════════════════════════════════

  КЛИЕНТ (человек, telegram_id UNIQUE)
    └── КЛЮЧИ 1..N (подписки; expires_at, revoked_at, max_devices)
          └── СЕРВЕРЫ 1..N через protocol_instances (mixed-protocol ок)
                └── УСТРОЙСТВА 0..max_devices (device_registrations)

  Б-01  Один клиент может иметь несколько ключей (мультипрофиль в клиенте).
  Б-02  Один ключ может давать доступ к серверам разных протоколов.
  Б-03  Клиент = человек с telegram_id: восстановление и напоминания
        работают через бота без участия админа.
  Б-04  Устройство регистрируется при первом подключении ключом.
        Enforcement лимита max_devices — НА СТОРОНЕ VPN-СЕРВЕРА при
        handshake/add-peer (плагин панели на VPS); клиент получает код
        отказа LIMIT и показывает экран «освободите устройство через бота
        (/devices)». Для pubkey-протоколов (awg, aivpn) лимит строгий по
        device_id; для password-based (wdtt) в MVP — эвристика сервера по
        одновременным сессиям (device_id в handshake wdtt появится позже).

## 5. KEY FILE v2 (КОНТРАКТ)
═══════════════════════════════════════════════════════════════════

Формат: INI-совместимый, генерируется панелью (/keys/{id}/download),
доставляется ботом, импортируется клиентом через file picker.

  [Hydra]
  Version   = 2
  KeyId     = <access_keys.key_id>
  ExpiresAt = YYYY-MM-DD HH:MM:SS
  MaxDevices= N
  ClientName= <display_name>          (для UI мультипрофиля)

  [Peer.<protocol>.<server_id>]       # по одной секции на instance
  Endpoint  = host:port
  Label     = "France · Hetzner"      (человеческое имя для UI)
  # protocol-specific:
  #   awg:   PublicKey, PrivateKey, + 27 AWG-параметров (Jc..ListenPort)
  #   wdtt:  Password, VKHashes (4 строки), Streams
  #   aivpn: Key = aivpn://<base64url(JSON s,k,p,i,n)>

  К-01  v1 (чистый WG-формат) понимается клиентом как legacy: только awg.
  К-02  Ключ самодостаточен: клиенту не нужен никакой сервер конфигурации.
  К-03  Продление/ротация = новый Key File через бота; клиент предлагает
        заменить профиль при обнаружении истечения.
  К-04  Секреты ключа хранятся в app-specific storage; Keystore — позже.
  К-05  Минимальный валидный v2 = [Hydra] + >=1 [Peer.*]; клиент обязан
        подключиться к минимальному ключу (один сервер, один AWG) — это
        базовый сценарий Фазы 2 и путь совместимости с legacy v1.

## 6. ЖИЗНЕННЫЙ ЦИКЛ КЛИЕНТА (END-TO-END)
═══════════════════════════════════════════════════════════════════

6.1 ПОКУПКА
    Клиент пишет боту → оплата (интеграция этапа 4) → бот создаёт клиента
    в панели (telegram_id) → выпускает ключ → присылает Key File v2 файлом.
    Dev-путь до Этапа 4 (Р-23): админ выпускает ключ в панели и передаёт
    .conf вручную (файл/QR); функционально эквивалентно выдаче через бота.

6.2 ИМПОРТ И ONBOARDING (2 экрана, без лишних вопросов)
    Экран 1: импорт .conf (file picker; QR — позже).
    Экран 2: готово. РФ-профиль split tunneling включён по умолчанию.
    После первого подключения — ОДИН раз snackbar: «Госуслуги и банки
    работают напрямую. Список можно изменить».

6.3 ПОДКЛЮЧЕНИЕ (Smart Connect, раздел 7)
    Кнопка AUTO → probe → score → pick → connect.
    Пользователь видит: страна, latency, статус. Ничего больше не нужно.

6.4 ПОВСЕДНЕВНАЯ РАБОТА
    Monitor: health каждые 25с. 2 провала → failover без разрыва TUN.
    Рейтинг пересчитывается: раз в 5 минут + немедленно при смене сети
    (Wi-Fi ↔ mobile). Foreground Service держит VPN при свёрнутом приложении;
    BOOT_COMPLETED → auto-start; смена сети → auto-reconnect.

6.5 ПРОДЛЕНИЕ
    Бот шлёт напоминания 7д/3д/1д/истёк → оплата → новый Key File →
    клиент предлагает заменить профиль (старый помечается истёкшим).

6.6 ПОТЕРЯ КЛЮЧА / СМЕНА ТЕЛЕФОНА
    /restore в боте (по telegram_id) → бот отдаёт активные ключи клиента
    файлами → импорт на новом устройстве. Админ не участвует.

6.7 БЛОКИРОВКИ (сценарии деградации, РФ)
    а) Заблокирован IP сервера   → Smart Connect перебирает другие
       серверы/протоколы из ключа; бот пушит новые endpoint'ы.
    б) Режут UDP (DPI)           → детект → AIVPN/WDTT.
    в) White list (только RU-домены) → детект → WDTT через VK TURN
       (VK в белых списках).
    г) Всё провалилось           → Emergency mode: диагностика,
       рекомендации, retry backoff 1м → 5м → 15м → 1ч в фоне.
    д) Заблокирован канал профилей → bundled РФ-профиль из APK.
    е) Обновление endpoint'ов при блоке IP: ТОЛЬКО новый Key File через
       бота (push) или ручной импорт. Молчаливой авто-замены серверов НЕТ
       осознанно: канал конфигурации, умеющий подменять сервера, при
       компрометации означает MITM всего трафика (Р-20).

## 7. SMART CONNECT (ПОЛНЫЙ АЛГОРИТМ)
═══════════════════════════════════════════════════════════════════

7.1 ENVIRONMENT PROBE (кэш 5 минут + при смене сети)
    - VK API доступен?            → wdtt в пуле / исключён
    - UDP-прямоток живой?         → awg/aivpn в пуле
    - TCP443 жив, UDP мёртв?      → признак DPI
    - google.com мёртв, gosuslugi.ru + vk.com живы? → white list mode

7.2 DPI DETECTION (три уровня)
    L1 Heuristic: TCP-handshake проходит, UDP-handshake таймаутит → DPI.
    L2 Active probe: UDP-пакет с известным payload; RST от middlebox →
       DPI активен; silent drop → firewall; ответ → порт жив.
    L3 History learning: per-network журнал успехов/провалов по протоколам;
       в знакомой сети заведомо мёртвые протоколы не пробуем первыми.

7.3 BACKEND PROBE (shadow-режим)
    Каждый кандидат поднимается в shadow-туннеле; меряем реальный RTT/loss/
    handshake-time через туннель (не TCP-пинг порта).
    Ограничение стоимости: probe не всех кандидатов, а top-3 по истории
    + 1 случайный (exploration); бюджет <= 3с на сессию. Полный обход всех
    кандидатов — только при Emergency и при первом подключении.

7.4 SCORING
    score = 0.6·latency_norm + 0.4·(1−loss) + персональный бонус
    latency_norm = 100/(100+RTT_ms)
    Персональный бонус: +0.1 протоколам с историей успехов в этой сети.
    server_load НЕ используется: клиент не знает панель (К-02), снимок
    load в ключе устаревает мгновенно, публичный status-endpoint создал бы
    точку блокировки и раскрытия инфраструктуры. Нагрузка учитывается
    косвенно: перегруженный сервер даёт худший RTT/loss в shadow-probe.

7.5 PICK + CONNECT + MONITOR
    top-1 → connect. Health каждые 25с (keepalive протокола).
    2 провала → failover: смена SOCKS5-апстрима под живым TUN
    (ОС не видит разрыва VPN; UDP-сессии и большинство TCP выживают через
    session persistence tun2socks; длинные TCP-сессии могут оборваться —
    приемлемый трейд: приложения переподключаются сами).
    Раз в 5 минут re-probe: текущий сервер хуже top-1 на 20% → плановый
    failover. Смена сети → полный пересчёт.

7.6 EMERGENCY
    Все кандидаты провалили → экран диагностики (тип сети, DPI да/нет,
    white list да/нет, таблица probe, рекомендации) + фоновый retry backoff.
    Здесь же клиент предлагает мастер «Включить WDTT (нужен VK, ~2 минуты)»,
    если VK-хеши не настроены (Р-21).

## 8. SPLIT TUNNELING И РФ-ПРОФИЛЬ
═══════════════════════════════════════════════════════════════════

8.1 ДОСТУПНОСТЬ: split tunneling виден ВСЕМ пользователям (не только
    advanced). На главном экране — тумблер «Российские приложения без VPN».

8.2 ДЕФОЛТ: РФ-профиль ВКЛЮЧЁН по умолчанию (целевой рынок — РФ).
    Onboarding НЕ спрашивает об этом (2 экрана, ноль трения).
    Одноразовый snackbar после первого подключения объясняет поведение.

8.3 РЕЖИМЫ: exclude (приложения мимо VPN) — основной; include (только
    выбранные через VPN) — advanced, пресет «Экономия трафика».

8.4 УПРАВЛЕНИЕ: категории-тумблеры (Гос / Банки / Платежи / Стриминги /
    Сервисы) + пресеты («Россия всё», «Только банки и гос», «Только своё»)
    + поиск и ручное добавление любого приложения.

8.5 НАЧАЛЬНЫЙ СОСТАВ РФ-ПРОФИЛЯ (пакеты верифицируются на живых устройствах;
    механизм обновляемый, верификация не блокирует релиз — Р-17):
    Гос:    Госуслуги ru.gosuslugi, ФНС, СФР
    Банки:  Сбер ru.sberbankmobile, Т-Банк com.idamobile.tinkoff,
            ВТБ ru.vtbbank.mcb, Альфа ru.alfabank.oavdo.amobile,
            Райффайзен, Газпромбанк
    Платежи: Mir Pay ru.nspk.mirpay, СБПэй
    Стриминги: Okko, Kion, Wink, More.tv
    Сервисы: Авито com.avito.android, WB com.wildberries.ru, Ozon,
            Яндекс Go ru.yandex.taxi, RuStore

8.6 ТЕХНИКА: Android VpnService.addDisallowedApplication() — трафик
    исключённых приложений физически не попадает в туннель (чище любых
    обманок антифрода). Desktop (Linux/Windows): split по доменам
    (DNS-based routing) — фаза 6, не MVP (Р-19).

8.7 REMOTE-ОБНОВЛЕНИЕ ПРОФИЛЕЙ
    - Публичный JSON в репо/CDN-зеркале (НЕ панель: клиент её не знает).
    - Структура: {version:int, updated_at, categories:[{id,name,
      apps:[{package,name}]}], presets:[...]}, version monotonic.
    - Клиент: pull при старте + раз в сутки; зеркала из списка в APK
      (таймаут 5с каждое); всё мертво → bundled-профиль из APK.
    - Подпись Ed25519: публичный ключ в APK; без подписи JSON не применяется.
    - Валидация схемы + чёрный список на клиенте: системные пакеты, пакет
      самого клиента и VpnService-зависимые игнорируются всегда.
    - Радиус влияния канала: ТОЛЬКО split-список. Ключи/сервера/крипто
      через этот канал не обновляются никогда.
    - Экстренно: пуш через бота «обновить профиль сейчас» (Этап 4).

## 13. БЕЗОПАСНОСТЬ И DR

  S-00  THREAT MODEL: self-hosted single-admin продукт. Основные векторы

        Украденный бэкап бесполезен без passphrase; украденная passphrase

  S-03  Секреты разработки (токены, пароли) в dev-фазе допустимы в рабочих
        каналах; ПОЛНАЯ РОТАЦИЯ перед продом — обязательна.
  S-04  Клиент: ключи в app-specific storage; Keystore — фаза polish.
  S-05  Split-профили: Ed25519-подпись + схема + чёрный список пакетов.
  S-06  Всё дублируется на GitHub (требование владельца проекта).
  S-07  Shell-safety в плагинах: run_with_stdin() вместо shell-интерполяции

  S-08  SSH host keys: fail-fast SecurityError если known_hosts отсутствует
        (Р-25). Emergency skip только для bootstrap с паролем.
  S-09  Auth middleware на ВСЕХ /api/v1/* endpoint'ах (Р-27). Rate-limit

## 15. ЗАФИКСИРОВАННЫЕ ПРОДУКТОВЫЕ РЕШЕНИЯ (ADR)
═══════════════════════════════════════════════════════════════════

  Р-01  Android first; iOS/macOS не поддерживаются никогда.
  Р-02  Стек клиента: Flutter + Go + Rust(aivpn). Не Rust/Tauri: весь
        VPN-стек уже на Go/Rust, переписывание = месяцы.
  Р-03  Единый VPN-слот: Hydra VpnService → tun2socks → SOCKS5-апстрим
        активного бэкенда. Failover без разрыва TUN.
  Р-04  AUTO-режим дефолтен; ADVANCED доступен всегда, не спрятан глубоко.
  Р-05  Split tunneling для всех; РФ-профиль default ON; onboarding без
        вопроса о РФ (2 экрана); одноразовая подсказка.
  Р-06  Remote-профили: публичный JSON + Ed25519 + bundled-страховка.
  Р-07  WDTT: 4 хеша фиксировано; 108 потоков адаптивно; хеши вводит
        пользователь вручную (экран с инструкцией).
  Р-08  Размер APK не оптимизируем.
  Р-09  Импорт ключа: файл .conf основной; QR позже.
  Р-10  Продление/восстановление: через бота; клиент не знает панель.
  Р-11  Background: Foreground Service + BOOT_COMPLETED + reconnect
        при смене сети. WorkManager не используем для VPN.
  Р-12  Рейтинг: re-probe раз в 5 минут + при смене сети; плановый
        failover при отставании текущего сервера на 20%.
  Р-13  Хранение профилей клиента: файл в app-specific storage (Keystore
        позже). Мультипрофиль: список ключей с переключением.
  Р-14  Monorepo hydra-suite; всё на GitHub.
  Р-15  Истёкший ключ: блок сразу + экран продления через бота.
        Grace period НЕТ (клиент получил 4 напоминания до истечения).
  Р-16  VK-хеши WDTT живут пока активен звонок (эмпирически 45+ дней,
        TTL отсутствует). Клиент детектит мёртвый хеш по провалу
        handshake и просит замену; таймер истечения не нужен.
  Р-17  РФ-профиль стартует best-effort списком; неточности правятся
        через remote-профиль за сутки. Верификация не блокирует релиз.
  Р-18  AIVPN: все mimicry-профили из assets/masks/ bundled в клиент
        (размер APK не оптимизируем, больше профилей = выше обход DPI).
  Р-19  Desktop split tunneling отложен до фазы 6 (Android-first MVP).
  Р-20  Обновление серверов/endpoint'ов: только новый Key File (бот или
        ручной импорт). Remote-канал обновляет ИСКЛЮЧИТЕЛЬНО split-список
        (8.7); подмена серверов через любой remote-канал невозможна.
  Р-21  WDTT в AUTO активен только если VK-хеши уже настроены пользователем.
        Без хешей AUTO работает на awg/aivpn; в Emergency клиент предлагает
        мастер «Включить WDTT (нужен VK, ~2 минуты)» как спасательный круг.
        Onboarding обещает «работает сразу в типичной сети», не «всегда
        без настроек».
  Р-22  /api/v1/client/* в панели — legacy/dev-заготовка; в prod-модели
        v4.1+ клиентом не используется; будет закрыт/удалён на Этапе 5.
  Р-23  Dev-путь без бота (до Этапа 4): админ выпускает ключ в панели и
        передаёт .conf вручную (файл/QR). Это официальный путь выдачи MVP.
  Р-24  WDTT-бэкенд НЕ входит в MVP-подключение (Фаза 3b): MVP = awg+aivpn.
        WDTT + VK-мастер приходят в Фазе 3c вместе с полным Smart Connect.
  Р-25  SSH host key verification: fail-fast SecurityError если known_hosts
        отсутствует. Emergency skip (skip_host_key_check=true) только для
        bootstrap с паролем в _ssh_run_once (Этап 2.5).
  Р-26  Shell-safety: никаких shell-интерполяций пользовательского input
        (label, client_id) в командах плагина. Только run_with_stdin() с
        JSON в stdin. Whitelist валидация: label [a-zA-Z0-9\\-_.], client_id
        проверяется по формату протокола (Этап 2.5).
  Р-27  Auth coverage: auth middleware на ВСЕХ /api/v1/* endpoint'ах, кроме
        /agent/metrics (Bearer token в header). Rate-limit на /api/v1/client/
        redeem + логирование попыток (таблица redeem_log) (Этап 2.5).
  Р-28  panel.yaml security секция: ssh_known_hosts, ssh_skip_host_key_check
        (default false). Загружается ServerManager при старте (Этап 2.5).
